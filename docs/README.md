## 📝 文档维护规范

### 命名规则
- ✅ 使用数字前缀: `01-`, `02-`, `03-`...
- ✅ 使用中文描述性名称
- ✅ 包含日期（如需要）: `功能需求提炼整合报告-2026-04-09.md`

### 存放规则
- **根目录**: 只保留 `README.md` 和 `status.json`
- **核心文档**: 放在对应分类文件夹
- **历史文档**: 移到 `old/` 归档
- **临时报告**: 测试完成后移到 `05-测试报告/`
- **过时文档**: 删除或归档到 `old/`

### 更新规则
1. **产品功能变更** → 更新 `01-核心产品文档/`
2. **技术架构变更** → 更新 `02-技术架构/`
3. **任务清单变更** → 更新 `03-开发规范/`
4. **部署方式变更** → 更新 `04-部署运维/`
5. **测试结果** → 添加到 `05-测试报告/`

### 禁止行为
- ❌ 在docs根目录创建新文档（除了README.md和status.json）
- ❌ 为每个小功能创建独立文档
- ❌ 创建临时报告后不清理
- ❌ 重复记录相同信息
- ❌ 在根目录保留已提炼的原始文档

## 💡 最佳实践

### 查找文档
1. 先确定文档类型（产品/技术/开发/部署/测试）
2. 进入对应文件夹（01-05）
3. 按数字前缀顺序浏览

### 添加新文档
1. 确定文档分类
2. 使用描述性名称
3. 添加到对应文件夹（01-05）
4. 更新本README的索引

### 清理文档
1. 定期review各文件夹
2. 删除过时内容
3. 合并相似文档
4. 历史文档移到 `old/`
5. 保持简洁

### 自动开发工作流
1. 查看 `status.json` 了解当前进度
2. 使用 `@auto-dev-executor` 指令执行任务
3. 任务完成后自动更新 `status.json`
4. 定期运行 `quality-validator.py` 验证质量
