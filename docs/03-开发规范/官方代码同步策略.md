# 官方代码同步策略与规范

> **制定时间**: 2026-04-21  
> **适用范围**: CRM 项目全体开发人员  
> **审查周期**: 每季度一次

---

## 📋 同步策略概述

### 采用方案：混合模式（Hybrid Approach）

**核心原则**：
- ✅ **核心框架**: 定期同步官方，保持稳定性
- ✅ **官方模块**: 跟随官方更新，获得新功能
- ✅ **CRM 业务模块**: 独立开发，不受官方影响
- ✅ **接口隔离**: 通过标准接口交互，降低耦合

---

## 🎯 同步频率

### 常规同步

| 类型 | 频率 | 时间 | 负责人 |
|------|------|------|--------|
| 小版本更新 | 每 2 周 | 周五下午 | 技术负责人 |
| 大版本更新 | 每月 | 月初第一个工作日 | 全体开发 |
| 安全补丁 | 立即 | 收到通知后 24 小时内 | 技术负责人 |
| Bug 修复 | 按需 | 评估后决定 | - |

### 特殊同步

- **紧急安全漏洞**: 立即同步
- **重要功能需求**: 评估后选择性合并
- **重大架构变更**: 谨慎评估，可能延后

## 🔧 同步流程

### 准备阶段

#### 1. 检查当前状态

```bash
# 进入 crm-fastapi 目录
cd crm-fastapi

# 查看当前分支和状态
git status
git branch

# 确保工作区干净
git diff
```

#### 2. 备份当前代码

```bash
# 创建备份分支
git branch backup-$(date +%Y%m%d)

# 或者打标签
git tag v-local-$(date +%Y%m%d)
```

### 执行阶段

#### 3. 获取官方最新代码

```bash
# 添加 upstream（如果还没有）
git remote add upstream https://gitee.com/fastapiadmin/FastapiAdmin.git

# 获取最新代码
git fetch upstream

# 查看差异
git log HEAD..upstream/master --oneline
```

#### 4. 在测试环境验证

```bash
# 创建测试分支
git checkout -b test-sync

# 合并官方代码
git merge upstream/master

# 启动测试环境
docker-compose up -d

# 运行自动化测试
pytest tests/ -v

# 手动测试关键功能
# - 登录
# - CRUD 操作
# - CRM 模块功能
```

#### 5. 解决冲突（如果有）

```bash
# 查看冲突文件
git status

# 逐个解决冲突
# 编辑冲突文件
vim <conflicted-file>

# 标记已解决
git add <conflicted-file>

# 完成合并
git commit
```

#### 6. 全面测试

**后端测试**：
```bash
# 单元测试
pytest tests/unit/ -v

# 集成测试
pytest tests/integration/ -v

# API 测试
pytest tests/api/ -v
```

**前端测试**：
```bash
cd frontend
npm run test
npm run build
```

**功能测试**：
- [ ] 用户登录/登出
- [ ] 权限控制
- [ ] 数据增删改查
- [ ] CRM 核心功能
- [ ] 代码生成器
- [ ] 工作流引擎

### 完成阶段

#### 7. 合并到主分支

```bash
# 切换回主分支
git checkout master

# 合并测试分支
git merge test-sync

# 推送到远程
git push origin master
```

#### 8. 清理

```bash
# 删除测试分支
git branch -d test-sync

# 更新文档
# - 更新 CHANGELOG.md
# - 更新 README.md（如有必要）
# - 记录同步日志
```

## ⚠️ 注意事项

### 同步前

1. **确保代码已提交**
   ```bash
   git status
   # 如果有未提交的更改，先提交或暂存
   git add .
   git commit -m "feat: ..."
   ```

2. **通知团队**
   - 在团队群组中通知即将同步
   - 建议大家在同步前完成手头工作并提交

3. **选择合适的时间**
   - 避免在发布前夕同步
   - 选择团队成员都在的时间
   - 预留足够的时间处理问题

### 同步中

1. **仔细检查冲突**
   - 不要盲目接受某一方的更改
   - 理解每个冲突的原因
   - 必要时咨询相关人员

2. **重点关注**
   - 数据库迁移脚本
   - API 接口变更
   - 配置文件变化
   - 依赖版本更新

3. **记录变更**
   - 记录重要的 breaking changes
   - 更新相关文档
   - 通知受影响的模块负责人

### 同步后

1. **全面测试**
   - 自动化测试必须通过
   - 关键功能手动测试
   - 性能测试（如必要）

2. **监控运行**
   - 观察错误日志
   - 监控系统性能
   - 收集用户反馈

3. **及时回滚（如有问题）**
   ```bash
   # 如果发现问题，立即回滚
   git reset --hard backup-YYYYMMDD
   
   # 或者
   git revert <merge-commit>
   ```

## 🚨 常见问题处理

### Q1: 合并冲突太多怎么办？

**A**: 
1. 评估冲突的复杂度
2. 如果太复杂，考虑重新基于官方代码开发
3. 或者分多次小批量合并

### Q2: 同步后功能异常怎么办？

**A**:
1. 查看错误日志定位问题
2. 检查是否是配置问题
3. 如果是代码问题，使用 `git bisect` 找出具体的 commit
4. 必要时回滚

### Q3: 官方的更新破坏了我们的定制功能怎么办？

**A**:
1. 评估是否真的需要这个官方更新
2. 如果只是部分功能，可以 cherry-pick 特定的 commit
3. 如果需要全部更新，重构定制功能以适配新架构
4. 考虑将定制功能提取为插件

### Q4: 如何避免频繁的合并冲突？

**A**:
1. 保持频繁同步（每 2 周）
2. 不要在核心框架文件中做大量修改
3. 将定制功能放在独立的模块中
4. 遵循官方的代码规范和架构

## 🎓 最佳实践

### 1. 保持模块化

```
app/
├── core/           # 核心框架（尽量不修改）
├── api/            # API 层（谨慎修改）
├── plugin/         # 插件目录
│   ├── module_*    # 官方模块（可同步）
│   └── module_crm_* # CRM 模块（独立）
```

### 2. 使用接口隔离

```python
# 不好的做法：直接依赖官方内部实现
from app.api.v1.module_system.user.service import UserService

# 好的做法：通过接口或抽象类
from app.core.interfaces import IUserService
```

### 3. 配置文件分离

```
env/
├── .env.example      # 官方模板（同步）
├── .env.dev          # 开发环境（本地维护）
├── .env.prod         # 生产环境（本地维护）
└── .env.crm          # CRM 特定配置（本地维护）
```

### 4. 文档化定制点

在 `docs/定制说明.md` 中记录所有对官方代码的修改：
- 修改的文件
- 修改的原因
- 可能的影响
- 同步时的注意事项
